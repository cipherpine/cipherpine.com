How Claude's usage limits actually work

Notes from the undocumented API.

> Justin · August 8, 2026 · 7 min read

If you use Claude Code on a subscription plan, you've probably hit the wall mid-task: the 5-hour window runs out — or worse, the weekly one — and the first you hear of it is the refusal. The obvious question — how much do I have left? — turns out to have no well-documented answer. Anthropic doesn't publish how the quota system works. But the official client has to get its numbers from somewhere, and that somewhere is an ordinary HTTPS endpoint that answers with JSON.

I've spent the last month building a quota monitor against that endpoint, so I've read its responses more carefully than most people would want to. This post is what I know: where the numbers live, what they mean, why third-party usage trackers so often disagree with the real limit, and what the endpoint tells you that no UI currently shows.

Where the numbers live

When you run /usage inside Claude Code, the client calls:

GET https://api.anthropic.com/api/oauth/usage
Authorization: Bearer <your OAuth token>
anthropic-beta: oauth-2025-04-20
User-Agent: claude-code/<version>

The token is the one the Claude CLI already keeps on your machine — this is the subscription-plan endpoint, not the API-key billing world. Two details matter if you ever poke at it yourself:

  • The anthropic-beta: oauth-2025-04-20 header is required.
  • The User-Agent matters. Requests without a plausible claude-code/<version> string land in an aggressively throttled bucket. The endpoint is effectively saying: this is for the official client.

The response is small. The shape, with values from a synthetic fixture:

{
  "five_hour":  { "utilization": 33.0, "resets_at": "2026-04-11T07:00:00+00:00" },
  "seven_day":  { "utilization": 80.0, "resets_at": "2026-04-18T07:00:00+00:00" },
  "seven_day_opus":   null,
  "seven_day_sonnet": { "utilization": 12.5, "resets_at": null },
  "limits": [ ... ]
}

That's the heart of it. Two things are worth noticing.

utilization is the server's number. It's a percentage computed by Anthropic, not a token count you're expected to tally yourself. Nobody outside Anthropic knows the exact formula (it clearly isn't raw token count — model, cache hits, and other factors weigh in). Every tool that shows you a percentage either reports this number or is guessing.

resets_at is nullable. A window you haven't touched may carry no reset time at all, because nothing is running down yet. Any tool that assumes it's always there breaks on quiet accounts.

The windows: 5-hour, 7-day, and per-model

The two headline windows are what you'd expect from Anthropic's own plan descriptions: a rolling ~5-hour “session” window and a 7-day weekly window. Both drain as you use Claude — on any surface — and each resets on its own clock.

The more interesting part arrived mid-2026: a generalized limits array that the older fields now duplicate. Each entry carries a kind (session-shaped kinds map to the 5-hour window; weekly kinds to the 7-day one) and an optional scope. An unscoped entry restates the headline windows. A scoped one carries scope.model.display_name — which is how per-model weekly quotas surface. If your plan has a model with its own weekly budget, this array is the only place that number exists. The legacy seven_day_opus / seven_day_sonnet fields are the older, hard-coded version of the same idea, and they're nullable because most plans don't populate them anymore.

Practical consequence: you can hit a limit that no summary screen shows you. I've tripped a per-model weekly cap while the headline weekly window sat far from full. If your tooling only reads the two headline numbers, that failure looks like a bug. It isn't — it's a scoped entry in an array most tools don't parse.

Why your usage tracker disagrees with Claude

The most popular Claude usage tools work a completely different way: they parse the JSONL transcript files Claude Code writes under ~/.claude/projects/ and add up tokens locally. That approach produces useful analytics — per-project breakdowns, historical cost estimates — but as a limit gauge it has a structural blind spot, and the issue trackers show users hitting it constantly (the most-starred tool in the space has an issue literally titled “shows normal usage, but limit is reached in claude. Why it is misleading?”).

Local logs only see this machine, this client. They don't see:

  • anything you did on claude.ai in the browser,
  • Claude Code running on your other machine,
  • other clients or surfaces tied to the same account.

The server's utilization number counts all of it. So a local tally can read 40% while the real window is exhausted — and no amount of parsing more carefully will fix that, because the missing usage never touched the local disk. The two approaches answer different questions. Local logs answer “what did this machine spend?” The OAuth endpoint answers “what will Anthropic let me do next?” If you care about the second question, only the server's number is truth.

When the server's numbers disagree with themselves

Honesty requires the next paragraph: the server's numbers are the authority, but they are not always coherent. Anthropic's own issue tracker currently has open reports of a daily/session limit exhausting while the weekly window shows a third used, weekly counters that reset on something like a 24-hour cycle, and reset times that don't match the plan's documentation. Client-side, you can't fix any of that — the honest move is to display what the endpoint said and when it said it, so at least the staleness and the contradiction are visible instead of laundered into a confident-looking bar.

The Codex side, briefly

OpenAI's Codex CLI has the same shape of story with different details. The usage endpoint lives at https://chatgpt.com/backend-api/wham/usage — note the host: chatgpt.com, not api.openai.com — because subscription-plan usage belongs to the ChatGPT backend, not the developer platform. The response carries a rate_limit object with primary_window and secondary_window, each self-describing: 

{ "used_percent": 25, "limit_window_seconds": 18000, "reset_after_seconds": 3600 }

The windows aren't named — they're sized. 18000 seconds is your 5-hour window; 604800 is the weekly one. There's also an additional_rate_limits array (per-model limits, named by limit_name), and a credits mechanism the UI surfaces as “resets available” — a limited ability to reset a window early.

What I built with all this

I wanted the server's numbers on screen at all times — not a dashboard to open, not a command to run, just a small always-on-top window that's there when the number starts to matter. So I built QuotaPane: a ~320px Rust window (Windows first; macOS/Linux build from source) showing both providers' windows as bars with reset countdowns, pace markers, and opt-in history sparklines, plus a headless CLI with --json and a --fail-at <N> flag that exits non-zero so scripts can gate long agent runs on remaining quota. It recently grew a second view that lists the Claude Code / Codex sessions running on your machine and whether each is working or waiting on you — derived from log metadata only, never message content.

Because a tool like this reads your credential files, the trust design is the actual product: read-only credentials, egress hard-allowlisted to exactly the two provider hosts, no telemetry — and those claims are numbered invariants machine-checked in CI against named tests on every push, not promises in a README. If the docs drift from the code, the build goes red. The whole sensitive surface is two small modules you can read in one sitting.

The result is a persistent, always-on-top view of where I stand with each subscription. It lets me load-balance across subscriptions and models, always know where the 5-hour and weekly windows sit, and plan work across every active project against what's actually left — instead of finding out at the refusal.

Caveats

Both endpoints are undocumented. Either vendor can change or break them without notice, and when that happens, honest tooling should say “stale” or “broken” rather than guess. Requests to the Claude endpoint present as the official client because the endpoint throttles anything else — you should know that's how every third-party tool in this space works, mine included. And everything here reads your own credentials, locally; nothing about your account leaves your machine that wasn't already going to the vendor.

If you've observed endpoint behavior that contradicts anything above, I'd like to hear it — the repo's issues are open, and this post gets corrected, not defended.
